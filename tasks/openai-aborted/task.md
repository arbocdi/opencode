# Диагностика частых сообщений «Прервано» при работе с OpenAI

## Что исследуем

Во время работы с моделями OpenAI (`gpt-5.5`, `gpt-5.6-sol-fast`) OpenCode периодически завершает текущий ответ и показывает в интерфейсе сообщение `Прервано`.

Нужно определить:

- кто инициирует прерывание: пользователь, OpenCode или OpenAI;
- какая исходная ошибка скрывается за общим сообщением `Прервано`;
- соответствует ли поведение известной ошибке OpenCode;
- почему уже настроенные timeout-параметры не предотвращают проблему;
- какие безопасные варианты исправления доступны.

## Итоговый диагноз

Основная причина подтверждена логами: OpenCode сам отменяет запрос, если OpenAI не прислал HTTP response headers за 10 секунд.

Типичная ошибка в логе:

```text
AbortError: Provider response headers timed out after 10000ms
```

Это не равнозначно пользовательскому нажатию `Esc`. В данном случае цепочка выглядит так:

```text
OpenCode отправляет запрос OpenAI
  -> OpenAI не успевает прислать HTTP-заголовки за 10 секунд
  -> внутренний header timeout вызывает AbortController.abort(...)
  -> transport возвращает AbortError
  -> UI классифицирует AbortError как MessageAbortedError
  -> русский интерфейс показывает «Прервано»
```

Логи также содержат прямые ответы OpenAI:

```text
service_unavailable_error
server_is_overloaded
Our servers are currently overloaded. Please try again later.
```

Это подтверждает, что задержки как минимум в исследованных эпизодах связаны с недоступностью или перегрузкой OpenAI, а 10-секундный timeout в OpenCode превращает задержку в немедленное прерывание.

По состоянию на 10 августа 2026 года в агрегированном `opencode.log` найдено:

- 39 событий `stream error` для `providerID=openai` с точным текстом `Provider response headers timed out after 10000ms`;
- 159 событий `stream error` для `providerID=openai` с кодом `server_is_overloaded`;
- 85 событий `message=cancel`, относящихся к явным локальным отменам за весь период лога.

Последнее число нельзя напрямую вычитать из первых двух: это отдельная категория событий за весь срок хранения лога. Оно нужно для проверки диагностического признака: ручная отмена логируется явно, тогда как автоматические 10-секундные timeout-события не имеют предшествующего `message=cancel`.

## Почему текущая конфигурация не помогает

В глобальной конфигурации timeout-параметры заданы для custom provider с ID `openai-api`:

```jsonc
"provider": {
  "openai-api": {
    "options": {
      "headerTimeout": 60000,
      "chunkTimeout": 60000,
      "timeout": 600000
    }
  }
}
```

Но проблемные запросы в логах имеют:

```text
providerID=openai
```

Provider ID является ключом конфигурации. Поэтому настройки `openai-api` применяются только к моделям вида `openai-api/...` и не переопределяют параметры встроенного provider `openai`, через который работают проблемные сессии.

## Связанные upstream issue и исправление

- Issue: <https://github.com/anomalyco/opencode/issues/29548>
- Основная issue о зависающих запросах OpenAI: <https://github.com/anomalyco/opencode/issues/29079>
- Исправляющий PR: <https://github.com/anomalyco/opencode/pull/37770>
- Patch commit: <https://github.com/anomalyco/opencode/commit/f36d1b4edd428150d60e734fa93848616af3979b>

PR `#37770` увеличивает стандартный OpenAI header timeout с 10 секунд до 300 секунд. Он был смержен в upstream `dev` 19 июля 2026 года.

До выполнения этой задачи локальный fork не содержал исправление: в `packages/opencode/src/provider/provider.ts` было задано `10_000`, а соответствующий тест также ожидал `10_000`. Активный OpenCode создан из локальной версии `0.0.0-dev-202607311227`, поэтому дата сборки сама по себе не означает наличие upstream-исправления.

У локального репозитория `origin` указывает на пользовательский fork `arbocdi/opencode`, а отдельный remote для `anomalyco/opencode` не настроен. Поэтому наличие актуального upstream-исправления проверено по текущей ветке `anomalyco/opencode:dev` и merged PR, а его отсутствие в fork на момент диагностики было подтверждено фактической константой и тестом в локальном checkout.

## Варианты исправления

1. Добавить timeout-настройку именно для встроенного provider `openai`. Это самый маленький локальный workaround и не требует пересборки OpenCode.
2. Изменить default в локальном fork с `10_000` на выбранные 45 секунд и обновить регрессионный тест. Это исправляет поведение для всех пользователей данной сборки.
3. Синхронизировать fork с актуальным upstream `dev`, если нужны и остальные upstream-изменения. Этот вариант шире и требует отдельного ревью конфликтов.

Выбран второй вариант со значением `45_000` миллисекунд. Отключать `headerTimeout` полностью обычно хуже: при реально зависшем запросе сессия может ждать бесконечно. Значение 45 секунд сохраняет защиту от вечного зависания, но дает OpenAI на 35 секунд больше для отправки первых HTTP-заголовков.
